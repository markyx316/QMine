# QMine 工作坊：一个 query 挖掘 agent 团队是怎么造出来的

> **文档说明**：正文用中文，技术名词保留英文原词（`StateGraph`、`superstep`、
> `checkpointer` 等），因为这些词在代码和官方文档里就是这么写的，翻译反而增加对照成本。
> 每一个数字都来自真实运行，可在 `runs/` 下查到出处。
>
> **建议的讲解顺序**：第 1、2 节讲"为什么"，第 3、4 节讲"基础设施与架构"，
> 第 5、6 节讲"跑一次是什么样"，第 7 节是全篇的核心设计思想，
> 第 8–10 节讲价值与证据，第 13 节是现场演示脚本。

---

## 1. 一句话

**QMine 是一个由 16 类 agent 组成的团队，在 LangGraph 上执行一套 12 阶段的
query 挖掘方法论；agent 负责描述与提议，而所有决定由可复算的度量做出。**

规模：`src/` 约 **37,000 行**、`tests/` 约 **15,500 行**、**739 个测试**、
**23 个 gate**、**15 次完整的真实运行**（最大一次 65,986 条 query、448 次模型调用、$7.91）。

---

## 2. 它要解决的问题，以及为什么不是"写一个 prompt"

**任务**：给定一份 query 日志（任何领域、任何语言），产出一套**可交付的意图体系** ——
类目定义、裁决规则、金标准、可部署的分类器、聚类树，以及一份能被审计的证据链。

**为什么一个大 prompt 做不到**，三个具体理由：

1. **它无法被检验。** 模型给出 20 个类目，你怎么知道这 20 个不是编的？
   QMine 的做法是：让两个**互不相通**的标注员各标一遍 3,000 行金标准，
   用 kappa 衡量这套体系**是否可教** —— live44 实测 kappa **0.8796**。
   这个数字不是模型自己说的，是两次独立判读之间算出来的。
2. **它没有记忆，也不可复现。** 同一份金融语料跑两次，得到 20 类和 19 类，
   **共享的类目代码为 0 个** —— 这是实测。所以任何"跑两次再对比"的分析都是在比噪声。
   QMine 把需要对比的数据**放进同一次运行**，用同一套体系打标。
3. **它会在你看不见的地方失败。** 本项目实测过的例子：一次运行的 gate 报告
   「覆盖率 100%」，而实际上 3,000 行金标准里有 225 行根本没标上 ——
   因为单标注员分支少写了一个字典键，覆盖率退化成了 `n/n`。
   **一个能自己报出"我这次没测"的系统，和一个默认报成功的系统，差别就在这里。**

## 3. 基础设施：LangChain 与 LangGraph 是什么

### 3.1 两者的关系（2026 年的现状）

常见误解是"二选一"。实际上它们是**同一家公司（LangChain Inc.）的两层**，
自 2025-10-22 的联合 1.0 发布起，**LangChain 的 `create_agent` 就跑在 LangGraph 的运行时上**。

| | LangChain | LangGraph |
|---|---|---|
| 定位 | **高层 API** | **低层运行时** |
| 提供 | 模型抽象、600+ provider 集成、LCEL 组合（`prompt \| model \| parser`） | `StateGraph`、循环执行、持久化、流式输出 |
| 计算模型 | **DAG**：数据顺序流过有向无环图 | **循环状态机**：节点是函数，边是路由，图可以回到自身 |
| 适合 | 一条确定的链路 | 需要分支、循环、断点、人工介入的长流程 |

**本项目使用的版本**：`langchain==1.3.15`、`langgraph==1.2.11`、
`langgraph-checkpoint-sqlite==3.1.1`。

### 3.2 LangGraph 的四个核心概念（QMine 全部用到）

**① `StateGraph` —— 共享状态的图**
节点是普通 Python 函数，接收 state、返回要合并进 state 的字典。
和链式调用的区别：链是"把上一步的输出传给下一步"，图是"**维护并演进一份共享状态**"。

**② `superstep` —— 并行推进的单位**
并行分支不是各跑各的，而是**一步一步同时推进**。这一点在 QMine 里是**载荷性**的：

> `langgraph 1.2.11` 里，汇合节点会**为每条入边各触发一次**，除非它们在同一个
> superstep 到达。所以 QMine 的两条分支被**强制保持相同长度**（各 2 个节点），
> 由 `test_the_two_branches_stay_the_same_length` 钉住。
> 长度不等的代价是浪费墙钟时间，而不是训练出两个分类器 —— 因为还有
> `phase_status` 兜底 —— 但让调度真正变好的是这个长度平衡。

**③ `checkpointer` —— 每个 superstep 存一次快照**
实现 `BaseCheckpointSaver` 接口，按 `(thread_id, checkpoint_id)` 存。
进程崩了可以从最后一个 checkpoint 继续。QMine 用 SQLite 后端，
文件就是每个运行目录下的 `checkpoints.sqlite`。

**④ `Send` API —— 动态扇出**
把一批子任务分发给同一个节点的多个并发实例。QMine 在**第 7 阶段命名**用它：
每个聚类叶是一个独立的命名任务，`Send` 让它们并发跑，
**且每个 agent 只看到自己那一片的 payload** —— 这个"只看到自己那份"是刻意的，见 §7.1。

### 3.3 QMine 在其上加了什么

LangGraph 给的是**执行**能力；它不管你的 agent 说得对不对。
QMine 加的是**证据与约束层**：

- **artifact store**：大对象（矩阵、表、模型）落盘，state 里只放指针
- **gate 系统**：24 个可复算的检查点，每个都记录 observed / threshold / message / remediation
- **六道 agent 输入门**：每一种 agent 产出都必须通过一个机械护栏
- **findings ledger**：run 级别的账本，一条发现只有在它自己的检查通过时才关闭
- **determinism**：三个固定 seed（metric=0 / viz=42 / replay=(0,1)），配置有 `config_hash`

## 4. QMine 的架构

### 4.1 12 个阶段，17 个图节点 —— 两者不是一回事

方法论是 **12 个阶段（p1–p12）**；图上是 **17 个节点**（`PHASE_NODES`），因为：

- **`p2` 展开成 5 个节点**：`p2a_taxonomy` / `p2b_gold` / `p2c_classifier` /
  `p2d_validate` / `p2e_subintents` —— 它们的依赖关系不同，必须分开调度
- **`p4`+`p5`+`p6` 合并成 1 个节点** `p456_tree` —— 见 §4.2，
  这是让两条分支等长的唯一分法
- 另有 `p0_foundation` 做准备，`p7` 通过 `Send` 扇出到 `p7_name_shard`（不在主列表里）

**讲解时值得强调**：图的形状是从"节点实际读什么"推出来的，
**不是照着方法论的示意图画的**。方法论说"阶段 4、5、6"，
但它们共享同一份中间数据、又都不需要模型调用，所以合成一个节点更好调度。

| 阶段 | 做什么 | 主要产出 |
|---|---|---|
| `p0_foundation` | 建运行目录、解析 provider、写 manifest | `run_manifest.json` |
| `p1_audit` | 语料画像、模板挖掘、风险预筛 | `corpus.parquet`、`template_groups.json`、`risk_screen.json` |
| `p2a_taxonomy` | **5 个研究员 agent 分头调研 → 架构师综合 → 批评者审查** | `taxonomy.json` |
| `p2b_gold` | **两名互不相通的标注员**标 3,000 行 → 裁判裁决分歧并写规则 | `gold.csv`、`gold_agreement.json` |
| `p2c_classifier` | 训练分类器（**两条分支在这里汇合**） | `centroid_classifier.joblib` |
| `p2d_validate` | 对抗性验证 | `adversarial_validation.json` |
| `p2e_subintents` | 少数语言子意图 | |
| `p3_represent` | encoder bake-off、稀疏块、alpha sweep | `emb_*.npy`、`representation.json` |
| `p456_tree` | K 定位、层级聚类、留出复现检验 | `hierarchy_meta`、`leaf_labels` |
| `p7_prepare/name/audit` | **`Send` 扇出**给每个叶命名，再盲审连贯性 | `tree_naming.json` |
| `p8_governance` | 执行合并/拆分等治理操作（**树在这里被改写**） | `governance.json` |
| `p9`–`p12` | 统一度量面板、部署包、漂移对比、报告、维护包 | 全部交付物 |

### 4.2 图的形状：为什么分叉，收益多少

```
        START
          │
    p0_foundation
          │
      p1_audit
          │
    ┌─────┴─────┐              ← 在这里分叉
    │           │
p2a_taxonomy  p3_represent      ← 自上而下 / 自下而上，各 2 个节点
    │           │                 （长度必须相等，见 §3.2）
 p2b_gold   p456_tree
    │           │
    └─────┬─────┘              ← p2c_classifier 是真正的汇合点
          │
   p2c → p2d → p2e → p7 → p8 → p9 → p10 → p10b → p11 → p12   ← 严格串行
          │
         END
```

**为什么这么分**：依赖关系是**从节点实际读什么推出来的**，不是照着方法论的图画的。
`p3_represent` 只消费 p1 的 `template_groups`；`p2c_classifier` 才是真正需要金标准的地方。

**实测收益**：live39 上，`p2a` 38 分钟 + `p2b` 69 分钟 = **107 分钟的 provider 延迟**
挡在 **39 分钟的纯 CPU 聚类工作**前面，而后者不依赖前者的任何输出。
分叉后这 39 分钟被藏进了等待窗口里。
**收益 ≈ 23%（174 → 134.5 分钟）是按各阶段实测时长做的调度模拟，
不是同一份语料串行/并行各跑一次的 A/B 实测** —— 分子分母都来自真实计时，
但"省下多少"这一步是算出来的。

### 4.3 状态模型：只放指针，不放数据

```python
class PipelineState(TypedDict, total=False):
    run_id: str
    phase: Annotated[str, furthest_phase]          # 自定义 reducer
    phase_status: Annotated[dict[str, str], merge_dict]
    completed_phases: Annotated[list[str], operator.add]
    ...
```

规则很硬：**任何大对象都不进 state**。想放 `np.ndarray`？改成放一个 artifact 指针。
`Annotated[..., reducer]` 是 LangGraph 的并发合并机制 —— 两条分支同时写 `completed_phases`
时，`operator.add` 决定怎么合并。

### 4.4 artifact store

八种落盘方式：`put_matrix / put_sparse / put_table / put_json / put_model /
put_text / put_markdown / put_figure`。每个都记录 producer 与 summary，
所以任何一个数字都能回溯到"哪个阶段、用什么产生的"。

### 4.5 断点续跑与"代"（generation）

崩了或被 gate 拦下时，`checkpoints.sqlite` 让你从最后一个 superstep 继续。
要重跑一个 run id 而**复用已付费的调用**，开一个新的 generation：

```bash
qmine new-generation RUN_ID --reason '为什么要放弃上一代'
qmine run --resume --run-id RUN_ID
```

旧的一代作为证据留下，`llm_cache/` 是 run 级别的，所以每一次付费调用都会重放。

## 6. 输入、输出、产物

### 输入（最少三样）

| | 说明 |
|---|---|
| **语料** | CSV / Parquet / XLSX，至少一列 query 文本 |
| **配置** | `configs/xxx.yaml`，声明列名、权重列、参照标签列；**必须 `extends: live.yaml`** |
| **领域画像** | `configs/domains/xxx.yaml`：分词器、encoder 候选、模板种子、风险类目、预期规模 |

可选但强烈建议：**流量权重列**（否则所有指标都在数"不同 query 条数"，
一个带六位数流量的头部词和一个只出现一次的词等权）。

### 输出（三层）

**① 中间产物**（每次运行都写，约 40 个文件）
`corpus.parquet`、`emb_*.npy`、`taxonomy.json`、`gold.csv`、`labels_full.csv`、
`representation.json`、`hierarchy_meta`、`tree_naming.json`、`governance.json`、
`findings.json`、`run_summary.json` …

**② 可交付文档**（full 模式约 10 份，fast 模式 3 份参考文档）
- `<domain>_自上而下_意图体系完整定义.md`
- `<domain>_自下而上_聚类树完整定义.md`
- `<domain>_query_挖掘结果.xlsx`（全量标注 + 9 个定义 sheet）
- `快照对比_漂移分析.md` / `分层对比_头尾结构差异.md`（多快照运行才有）

**③ 可部署物**
`deployment.json` + 质心矩阵（**实测 51 次运行：37–481 KB，中位 74 KB**；`ai04` 是 481 KB）。推理就是
`encode(query) → hybrid transform → argmax(x @ centroids.T)`，
margin 低于 0.02 的行走兜底路径。

## 7. 核心设计：**agent 描述，度量决定**

这是全篇最重要的一节。QMine 的立场是：
**agent 很擅长"描述"和"提议"，但不应该有"决定"的权力。**

### 7.1 六道门 —— agent 产出的六种入口，每一道都有机械护栏

| 门 | 模块 | 护栏 |
|---|---|---|
| **prose**（叙述） | `agents/verify.py` | 每个数字都要能在 artifact 里查到，查不到就拒绝 |
| **observation**（观察） | `ops/checks.py` | 必须附一个**可执行的断言**；断言没跑通就丢弃 |
| **grid proposal**（网格提议） | `ops/propose.py` | 提议者**看不到分数**；新候选必须比现任好过 2 个标准误 |
| **deliverable edit**（文档编辑） | `ops/edits.py` | **唯一的写权限**，且只能改 `.md`，不能碰 artifact、不能碰代码 |
| **narrative**（报告） | `report/narrate.py` | 同 prose，且覆盖率要披露 |
| **prescription**（处方） | `ops/governance.py` | 必须带证据；执行与拒绝都要记录 |

三条到处都适用的规则：
1. **severity 是置信度，不是权限**
2. **一个"被确认"的检查，只证明那条断言不成立，不证明存在缺陷**
3. **`ops/edits.py` 是唯一写权限**

**"每个 agent 只看到自己那份"的具体例子**：第 7 阶段命名时，`Send` 给每个 agent
的 state **只有它自己那片的 payload**。这不是节省 token —— 是为了让"这个叶叫什么"
成为一次**独立判断**，而不是被别的叶的命名带跑。

**实测的价值**：`p7_risk_independently_found` 这个 gate 检查的是
「风险内容是否被一个**从未被告知要找风险**的 agent 标了出来」。
`ai04` 上它 PASSED —— 这是一次真正独立的确认。

### 7.2 23 个 gate

每个 gate 记录 `observed` / `threshold` / `message` / `remediation`，并有三种非通过状态：

- **WARNED**：测到了，但不阻断（例：`p1_minority_language_risk` —— 少数语言占 0.8%）
- **SKIPPED**：这次没做（例：fast 模式下的 `p2b_kappa`，措辞是「**未测量**」）
- **N/A**：这个组件本次没跑，**绝不报 PASS**

> **这一条是整个设计的缩影**：`verify_run.py` 对 `ai04` 的结果是
> **PASS 19 / N-A 6 / SKIP 2 / FAIL 1**。那 6 个 N/A 是 fast 模式跳过的组件 ——
> 如果它们报 PASS，读者会以为这些检查通过了。**"没做"和"做了并通过"必须长得不一样。**

### 7.3 交付分区（delivered partition）

`p8` 会**改写整棵树**。所以：

> **任何以"最终"呈现的东西，都必须来自交付分区。**

`ai04` 的实测：`p7` 命名了 156 个叶，`p8` 执行 56 项治理后交付 **154 个**。
引用 156 就是在描述一棵**已经不存在的树**。
本项目为此吃过亏：一个 gate 放在"破坏它自己不变量的操作"之前，**它什么都保证不了**。

### 7.4 findings ledger

run 级别的账本。一条发现被记下后，**只有它自己的检查通过时才关闭**。
`ai04` 的账本是**空的**（`n_open=0`）—— 因为 fast 模式关掉了阶段观察者，
而观察者是最主要的记账来源。作为对照，full 模式的 `live42` 有 **53 条待处理、21 条已确认**。
（写这份文档时我一度把对照运行的数字当成了 `ai04` 的 —— 这正是
`verify_run.py` 要求"必须带一个已知有问题的运行做对照"时最容易犯的错。）
存在的理由很直接：曾经有一个批评者 agent **在缺陷上线前就发现了它**，
而没有任何东西读它的输出。**没人能处理的发现，至少不能消失。**

## 8. 新颖性与贡献

| # | 贡献 | 具体是什么 |
|---|---|---|
| 1 | **把方法论编译成图，而不是编成 prompt** | 12 个阶段、23 个 gate，每一步的前提都是可检查的 |
| 2 | **agent 与决定权分离** | 六道门 + 机械护栏；agent 没有一处能直接改参数 |
| 3 | **"没测"与"测了且通过"在产物里可区分** | SKIPPED / N-A / WARNED / PASS 四态；fast 模式下 kappa 是**缺失**而非 1.0 |
| 4 | **对比必须同框** | 两次运行共享 0 个类目代码是实测 → 需要对比的数据放进同一次运行 |
| 5 | **对比轴是显式的** | `comparison_axis: time \| stratum` —— 同一套计算，两套措辞；把"抽样差异"读成"时间变化"是会出人命的错 |
| 6 | **测试即不变量文档** | 739 个测试，每一个的 docstring 都记录它是为哪次真实缺陷写的 |
| 7 | **可移植到任意语料** | 阈值不许从单一语料引入（`test_gates_do_not_import_thresholds_that_only_fit_one_corpus`）；已在 6 个语料上跑通 |

## 9. 对生产力、产品与运营的价值

### 9.1 生产力：把"人月"换成"小时 + 十美元"

| | 传统做法 | QMine |
|---|---|---|
| 3,000 行金标准双标注 | 2 名标注员 × 数天 | `p2b`，一次运行内完成 |
| 一套 20+ 类的意图体系 | 分析师数周 | **3.5 小时 / $7.91**（`ai04`，65,986 行） |
| 一致性检验（kappa） | 常常直接跳过 | 每次 full 运行都算，live44 = **0.8796** |
| 可部署分类器 | 另一个项目 | 同一次运行的副产品（质心矩阵 37–481 KB） |

**15 次真实运行的成本区间**：fast 模式 **$3.01–$7.91**，full 模式 **$1.10–$65.05**。
最大一次 65,986 条 query，3.5 小时。

### 9.2 产品：它能回答的问题，以及一个真实例子

`ai04` 的实测结论：**该 AI 助手 76.8% 的流量不是检索意图** ——
工具按钮（29.6%）、上下文缺失的片段（29.0%）、建议回复气泡（18.2%），
而这三类只占 **18.7% 的条数**。

**这个结论只有同时看"条数占比"和"流量占比"才看得见**，
而它直接改变资源投向：只看流量会把钱投给工具链，只看条数会投给问答质量。

更进一步：把 24 个意图分成"搜索可表达"与"助手原生"后 ——
按流量看助手是**工具界面**（头部 82.4% 是搜索做不到的事），
按需求种类看它是**搜索框**（长尾 79.2% 是搜索型问题）。**两个都对，服务的是不同人群。**

### 9.3 运营：三个可直接落地的动作

1. **日志侧打标隔离**：`👌 好的，继续吧` 与 `🆗 行，继续吧` 合计超过 400 万 PV，
   出现在 **33 个垂类中的 32 个** —— 它是产品自己的建议回复气泡被记进了 query 日志。
   如果日志用于需求分布或推荐输入，这会**系统性污染**它。
2. **安全策略要重做**：搜索拦的是"检索词"，助手必须拦"生成请求"。
   实测 `成人色情` 垂类头部有 **15.7% 的流量**是图像生成类表述。
3. **一条需要人看的记录**：`minor_sexualisation` 命中 1 条 —— 一名自述 15 岁的初中生
   询问自己的身体尺寸，而**导出自带的类目体系把它归在"生活和情感/两性知识"**，
   一个没有未成年人专门处理的通用桶。**一个只命中一次的类别仍然值得声明。**

## 11. 局限（工作坊上要主动讲的）

1. **两条路线的一致度是语料相关的。** `ai04` 上 121 个家族里只有 18 个"两路线一致"，
   原因是这份语料 query 极短，"长得像"和"意图一样"分开了 ——
   `工作`、`房子`、`塑料`、`海豚` 会被聚到同一个叶（叶名就叫`短词查询`）。
2. **fast 模式确实少了东西**：kappa、对抗性验证、阶段观察者、叙述报告、交付审计。
   少的是**检查**，不是分析 —— 但 `ai04` 因此没有观察者，也就没人发现
   alpha 的选择处在刀锋上（α=0.0 仅以 0.3% 之差落选，而它的稳定性更高）。
3. **59 个风险叶未经人工复核。**
4. **agent 会失败。** `researcher_log_reading` 这个角度在 **39 次**实际跑过它的运行里，
   **37 次产出了结果**，**2 次耗尽全部重试**（`ai03`、`med03`），
   另有 **10 次是先失败再重试成功** —— 失败一次再恢复是这个角色的常态。
   系统的应对是"这个角度没有贡献，体系在没有它的情况下设计"——
   **优雅降级，并且说出来**。
5. **它不做因果。** 它能说某一类占比高或低，不能说为什么。

## 12. 一句话总结

**QMine 不是"用 AI 做分析"，而是"用 AI 做描述，用度量做决定，并且让'没做的事'
在产物里看得见"。** 15 次真实运行、739 个测试、23 个 gate 都是为这一句话服务的。
